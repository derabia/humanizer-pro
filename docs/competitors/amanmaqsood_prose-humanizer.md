## 2. Form factor

It is a **hybrid**: an agent skill (`SKILL.md` present at repo root, `SKILL.md:1-4`, YAML frontmatter with `name: prose-humanizer`) bundled with a genuine **npm CLI package** (`package.json:12-16` declares `bin.prose-lint` and `bin.prose-humanizer` both pointing at `bin/prose-lint.js`). The CLI (`bin/prose-lint.js`, 330 lines) is a real, testable Node.js program with subcommands `report`, `analyze`, `fix`, `stats`, `scan`, `profile`, and a deprecated `score` (`bin/prose-lint.js:34-42`).

Hosts targeted: Claude (Code and claude.ai), Codex, Gemini CLI, Cursor — `README.md:22` and the install matrix in `INSTALL.md:52-56`. It ships host-specific adapters: `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (Claude Code plugin manifests), `.codex-plugin/plugin.json` (Codex/ChatGPT plugin manifest with `interface.defaultPrompt` etc.), `agents/openai.yaml` (OpenAI agent interface config), and `commands/gemini/prose-humanizer.toml` (a Gemini CLI slash-command adapter that just activates the skill, `commands/gemini/prose-humanizer.toml:3`). It is largely agent-agnostic at the skill level (Markdown instructions any Agent-Skills-compatible host can read) but the CLI itself is a **pure rule-based, non-LLM tool** — `analyzeText` in `lib/prose-core.js:348-381` is deterministic regex/word matching with no model call anywhere in the codebase.

## 3. Languages & varieties covered

No Arabic support anywhere in the repository (no `ar-*` files, no Arabic strings found in any pattern, reference, or test file). English is the only language with an automated pattern catalog: `lib/prose-core.js:349` — `analyzeText` returns `[]` immediately "if (!config.language.toLowerCase().startsWith("en"))". The skill-level Markdown guidance (not the CLI) is explicitly designed to be language-agnostic for editing: `references/scope-and-language.md:5-9` — "The bundled pattern linter is English-only. For other languages, use semantic, voice, and destination checks without applying its English vocabulary or syntax rules." Non-English support is demonstrated only through generic voice/fidelity preservation, tested with **one Spanish fixture**: `evals/benchmark.json:69-77` (`language-preservation`, instruction "Preserve Spanish and the stated voice. Do not translate or standardize it."), and a Spanish voice-profile unit test (`tests/prose-core.test.js:187-196`, "non-English voice profiles omit English lexical features"). There is no dialect-routing system, no MSA/dialect distinction, and no variety-specific reference files of any kind.

## 4. Pattern catalog

The machine-readable catalog lives in `rules/patterns.json` and contains **22 distinct pattern/rule entries** (confirmed by `grep -c '"id":' rules/patterns.json` = 22), spanning categories `language`, `structure`, `filler`, `rhetoric`, `clarity`, `evidence`, `communication`, `ending`, `format`, `punctuation` (`rules/patterns.json:8-222`). One of those 22 (`tier1-vocabulary`, `rules/patterns.json:6-25`) is itself a 54-word exclusion list (`values` array, `rules/patterns.json:12-23`), so the effective phrase/word surface is much larger than 22 literal strings. Separately, `rules/patterns.json:224-233` defines **8 `safeFixes`** — deterministic, reversible mechanical substitutions (e.g. `"in order to" → "to"`).

The companion narrative guide `references/patterns.md` documents a **broader, 23-row "High-confidence structural patterns" table** (`references/patterns.md:20-44`) that includes several patterns with no machine rule at all — e.g. "Forced grouping", "Synonym cycling", "False range", "Diff-anchored prose", "Fractal summary", "Hollow content", "Humanizer signature", and "Promotional varnish" (`references/patterns.md:28,35,37,39,41,43,23` — no matching `id` in `rules/patterns.json`). A second table, "CLI rule map" (`references/patterns.md:270-293`), maps exactly the 22 machine rule IDs to one-line review-signal descriptions, 1:1 with `rules/patterns.json`.

**Before/after examples:** the pattern guide table gives a "Common shape" and "Better move" column per pattern (`references/patterns.md:20-44`), e.g. "significance inflation... 'pivotal moment,' 'testament to'... State the event and consequence at the scale the evidence supports." — these are illustrative fragments, not full before/after passages. The 8 `safeFixes` are literal, exact substitutions (`rules/patterns.json:224-233`).

**IDs:** yes, every pattern and every safe fix has a stable string `id`/`match` key (`rules/patterns.json`), and `scripts/validate_skill.py:92-98` enforces that every rule ID is documented in `references/patterns.md`, and (`:99-107`) that every regex compiles.

**Provenance:** project-level only, not per-pattern. `ACKNOWLEDGMENTS.md:5-19` lists eight upstream projects reviewed (blader/humanizer, petergyang/no-ai-slop, aashaexo/soundshuman, jalaalrd/anti-ai-slop-writing "reviewed for comparison only", hannsxpeter/humanizer, HopLittleBunny/write-like-me, milock/humanizer, AshwinSathian/humanize-writing-skill) plus a v1 inspiration article, but individual pattern IDs carry no citation back to a specific upstream line, unlike humanizer-pro's `docs/PROVENANCE.md`.

**False-positive carve-outs:** `references/patterns.md:5-16` ("Preserve before changing" — do not flag polished grammar, a single em dash/semicolon/rhetorical question, passive voice with unknown actor, a real developed objection, deliberate repeated openings, or watched language inside a quotation/title/code/historical source) and `references/patterns.md:57` ("Treat vocabulary as a context-sensitive warning. A technical term, quotation, title, or established voice can justify any word.").

**Data-quality note:** the `tier1-vocabulary` word list in `rules/patterns.json:13-22` (54 words) and the "Exclude by default" list in `references/patterns.md:59` (44 words) have drifted — the JSON list contains words absent from the prose list (`intertwine`, `entwine`, `espouse`, `exemplify`, `underpin`, `tempest`, `whimsy`, `uncover`, `nuanced`, `commendable`, `poignant`, `unwavering`), meaning the human-readable guide understates what the CLI actually flags.

## 5. Detection

Yes — a real, parseable, deterministic detector exists as source code: `analyzeText` in `lib/prose-core.js:348-381`, invoked by the `report`/`analyze`/`score`/`scan` CLI commands (`bin/prose-lint.js`). It is explicitly **not an authorship/AI-likelihood detector**: every report JSON object sets `authorshipClaim: false` (`lib/prose-core.js:421`, `bin/prose-lint.js:119`) and `calibration: "uncalibrated-review-signal"` (`lib/prose-core.js:423`).

**Scoring:** `report`/`buildReport` (`lib/prose-core.js:412-445`) computes `weightedDensityPer100Words` — a weighted-finding density metric explicitly labeled uncalibrated, not a 0–100 "AI score." A deprecated 0–100 **compatibility** score exists only in the CLI's `score` command: `bin/prose-lint.js:113-128`, `Math.round(Math.min(100, report.metrics.weightedDensityPer100Words * 6))`, carrying `deprecated: true` and the warning "This 0-100 score is an uncalibrated compatibility metric. Use report instead." (`bin/prose-lint.js:120-121`). `references/cli.md:16` also calls `score` "a deprecated v3 compatibility command for one major release."

**Character/line offsets:** yes, exact spans. Each finding carries `line`, `column`, `start`, `end` (absolute character offsets into the source text) — `lib/prose-core.js:363-372`, produced by the line/segment tokenizer `parseProseSegments`/`lineRecords` (`lib/prose-core.js:120-131, 238-328`). Findings are deduplicated and grouped by overlapping span with a max-weight rollup (`lib/prose-core.js:391-409`), and the report also reports `affectedCoveragePercent` (`lib/prose-core.js:436-438`).

**No language auto-detection**: unlike humanizer-pro's `lang.js` heuristics, this repo requires the caller/config to declare `language`; `analyzeText` silently returns no findings for anything not starting with `"en"` (`lib/prose-core.js:349`).

## 6. Modes & output contract

`SKILL.md:10-18` defines seven request "modes" the skill routes to: **Draft**, **Rewrite**, **Voice match**, **Detect**, **File**, **Repository audit**, **Embedded**. This is broader than a simple detect/rewrite/edit split. A mandatory "Verify independently" pass runs after drafting/editing (`SKILL.md:87-95`, five-step evidence diff) followed by a separate `references/eval.md` pass with three axes (fidelity as a hard gate, voice fit, naturalness — `references/eval.md:5-42`) — functionally a second-pass self-review, though not literally "run it twice" like humanizer-pro's mandatory second-pass audit.

Output is **freeform prose by default**, but the CLI commands emit **structured JSON** on `--json` (`bin/prose-lint.js:130-299`, e.g. `report`, `analyze`, `stats`, `scan`, `profile`). There is no diff-mode output; `file` mode returns edited prose plus "a short verification summary" (`references/eval.md:47`). It is CLI-driven for the deterministic parts (`bin/prose-lint.js`) and prompt/skill-driven for the generative parts; there is no web UI or hosted API — pure local files.

## 7. Voice matching / persona profiles

Yes, and it is one of the more developed parts of the repo. `references/voice.md` (53 lines) governs voice-sample handling: explicit-only sample acceptance ("Do not search parent folders... without an explicit request", `references/voice.md:7`), per-source provenance recording (label/date, typed/dictated/AI-edited/translated/collaborative/unknown, complete-vs-excerpt, destination/audience/topic — `references/voice.md:9-15`), and a feature-level confidence model rather than one global score (`references/voice.md:19-29`). It explicitly forbids stereotyping dialect/nationality/age/gender/profession/education (`references/voice.md:37-39`).

Programmatically, `buildVoiceProfile` (`lib/prose-core.js:524-629`) computes weighted features (sentence length mean/variation, paragraph words mean, type-token ratio, contraction rate, first-person rate, question/exclamation rate per sentence) with per-source-type evidence weights (`lib/prose-core.js:533-541`, e.g. dictated: `sentence:1, paragraph:0.4, lexical:0.85, punctuation:0.2`) and a `low/medium/high` confidence label derived from weighted sample counts (`lib/prose-core.js:565-569`). There is no named "persona" library (no casual/professional/technical/blunt presets like humanizer-pro's five voice profiles); voice is always sample-derived.

## 8. Preservation & SEO safety

**SEO: none.** No SEO mode, no keyword-protection list, no meta-title/schema/FAQ handling anywhere in the repo (confirmed absent by full-text read of every reference and rule file; nothing matches "SEO", "keyword", "meta description", or "schema.org").

**Preservation** is strong and code-enforced at the CLI layer. `references/file-safety.md:5-16` lists protected content (frontmatter, code/config/data, URLs/link destinations, quotations, data tables, HTML/MDX tags and props, generated/vendored/lockfile content). This is implemented mechanically by `parseProseSegments` (`lib/prose-core.js:133-327`), which strips inline code spans, link destinations, HTML tags with brace/quote-aware state tracking, quotation ranges, tables, block quotes, indented code, reference-link definitions, and `<!-- generated:start/end -->` marker regions before any rule ever sees the text. `applySafeFixes` (`lib/prose-core.js:474-483`) applies its 8 mechanical fixes only inside those already-carved-out prose segments, verified by unit tests preserving links, tables, HTML props, generated sections, and inline code (`tests/prose-core.test.js:77-118`).

**Validator:** yes, but it is a benchmark/invariant harness rather than a before/after validator script like humanizer-pro's `validate.js`. `scripts/run_benchmark.js:47-83` checks `required`/`forbidden`/`protected` literal substrings, `requiredOrder`, `forbidUnexpectedNumbers`, `forbidFirstPerson`, and `maxEditRatio` (normalized edit distance) per fixture case (`evals/benchmark.json`).

## 11. Ethics

Framing is unambiguously "better writing," not detector evasion. `SKILL.md`'s frontmatter description ends: "do not use it to infer AI authorship or promise detector evasion." (`SKILL.md:4`). `README.md:36-37` (a GitHub `[!IMPORTANT]` callout): "Prose Humanizer is not an AI detector and does not promise detector evasion. Detector scores do not establish authorship. Judge writing by factual fidelity, voice fit, specificity, clarity, and reader experience." Every CLI report/score object literally embeds `authorshipClaim: false` (`lib/prose-core.js:421`, `bin/prose-lint.js:119`). `SKILL.md`'s final line states the tool "Never describe output as undetectable, human-authored, or guaranteed to pass a detector."

The one detector-evasion-adjacent trace is historical/citational: `ACKNOWLEDGMENTS.md:5` credits "Ruben Hassid's article ['Can you detect AI?'](https://ruben.substack.com/p/how-to-bypass-ai-detectors)" as inspiration for v1's pattern catalog — the URL slug literally reads "how-to-bypass-ai-detectors" — but the acknowledgment frames it only as the source of "its catalog of recurring generated-writing habits," not as an evasion goal, and the rest of the design documentation (`references/research.md:5-11`) explicitly excludes detector scores from the project's objective, citing OpenAI's classifier withdrawal and adversarial-robustness research.

**Fact invention:** forbidden and machine-tested, not just asserted. `SKILL.md`'s evidence-boundary section states a rewrite "fails if it invents a narrator, experience, motive, relationship, cause, outcome, comparison, quotation, citation, statistic, or customer reaction." `scripts/run_benchmark.js:69-77` enforces `forbidUnexpectedNumbers` and `forbidFirstPerson` programmatically against reference fixtures (`evals/benchmark.json`), and `tests/benchmark.test.js:29-44` proves an invented literal ("Revenue rose by 37%") is caught and fails the suite.

**No detector-name marketing.** Nowhere in the repo — README, SKILL.md, ACKNOWLEDGMENTS, or PRIVACY/TERMS — is Turnitin, GPTZero, Originality.ai, Copyleaks, or any specific detector product named as a target to beat.

## 12. Notable ideas worth borrowing

- **Overlap-group deduplication with max-weight rollup and coverage percentage.** `overlapGroups` (`lib/prose-core.js:391-409`) merges overlapping findings into groups and reports `affectedCoveragePercent` (`lib/prose-core.js:412-438`) — gives a single "how much of the prose is actually flagged" number instead of a raw finding count. Humanizer-pro's detector has no equivalent overlap/coverage metric.
- **Segment-parsing as the single source of truth for both linting and fixing.** `parseProseSegments` (`lib/prose-core.js:238-327`) is called by both `analyzeText` (detection) and `applySafeFixes` (mechanical rewriting), and fixes are applied in *reverse segment order* (`lib/prose-core.js:479` — `for (const segment of [...segments].reverse())`) so earlier-segment offsets stay valid after later edits. This avoids offset-invalidation bugs that plague naive string-replace approaches.
- **Fail-closed, schema-validated project configuration.** `loadConfig` (`lib/prose-core.js:41-106`) rejects unknown top-level keys, unknown rule IDs in `disabledRules`/`severityOverrides`, and invalid `channel`/`language`/`threshold` values outright, backed by a JSON Schema with `additionalProperties: false` (`schemas/prose-humanizer.schema.json:6`). Humanizer-pro has no equivalent per-project config file or schema at all — worth considering for repo-level tuning (exclusions, severity, thresholds) without touching the skill itself.
- **Build-time consistency checks between rule catalog and documentation.** `scripts/validate_skill.py:92-98` fails the build if any `rules/patterns.json` rule ID is undocumented in `references/patterns.md`, and `:99-107` fails the build if any regex pattern doesn't compile. Humanizer-pro's `tools/check-skill.js` validates frontmatter/cross-links but has no rule-catalog-to-doc parity check or regex-compile check — directly applicable to `rules/patterns.json`... i.e., humanizer-pro's own pattern references.
- **Reproducible deterministic benchmark with explicit machine-checkable invariants**, separate from subjective quality: `evals/benchmark.json` cases carry `required`, `forbidden`, `protected`, `requiredOrder`, `forbidUnexpectedNumbers`, `forbidFirstPerson`, and `maxEditRatio` (normalized edit distance cap) fields, executed by `scripts/run_benchmark.js:43-83`. This is a stronger, more specific invariant vocabulary than humanizer-pro's own eval harness and would directly harden humanizer-pro's `evals/benchmark.json` equivalent.
- **Blinded, seeded pairwise human-evaluation kit with a separate answer key.** `scripts/prepare_pairwise.js` builds a `ballot.json` (candidate identity hidden, left/right randomized via a seeded PRNG) and a separate `key.json` (kept from raters until scoring is done) — `scripts/prepare_pairwise.js:35-67`. This is a direct, ready-made answer to humanizer-pro's own documented weak spot 3.11 ("Eval grading was done by the builder's own agents"): a mechanism for genuinely blinded third-party grading.
- **CI matrix across Node 18/20/22 plus a real Windows installer smoke test** (`.github/workflows/validate.yml:13-16, 47-69`), including asserting specific installed files exist and running the CLI's `--help` post-install. This directly answers humanizer-pro's weak spot 3.9 ("Node 18 was never actually executed") — the pattern (matrix CI actually running the claimed minimum version) is copyable regardless of hosting.
- **Provenance-weighted, privacy-safe voice profiles.** `buildVoiceProfile` (`lib/prose-core.js:524-629`) stores only SHA-256 hashes, source type, per-feature confidence, and weighted evidence counts — never raw prose (`schemas/voice-profile.schema.json:12` hard-requires `rawProseStored: const false`). The evidence-weight table by source type (typed/dictated/ai-edited/translated/collaborative — `lib/prose-core.js:533-541`) is a genuinely useful idea: it treats "how much can I trust this sample for this specific feature" as a matrix, not a single confidence number.
- **Deprecation discipline with an explicit compatibility shim.** The old v3 `score` command is kept working, marked `deprecated: true` in its own JSON output, with a stated removal version (v5) — `bin/prose-lint.js:113-128`, `references/cli.md:16`. A concrete pattern for humanizer-pro if its own CLI flags or output shapes ever need to change without breaking existing callers.

## 13. Weaknesses

- **Tier-1 vocabulary list drift between the machine rule and the human-readable guide.** `rules/patterns.json:13-22` (54 words) and `references/patterns.md:59` (44 words) disagree — 12 words the CLI actually flags (`intertwine`, `entwine`, `espouse`, `exemplify`, `underpin`, `tempest`, `whimsy`, `uncover`, `nuanced`, `commendable`, `poignant`, `unwavering`) are missing from the documentation a human editor would read.
- **Roughly a third of the "High-confidence structural patterns" documented in `references/patterns.md:20-44` have no machine rule at all** (e.g. "Forced grouping," "Synonym cycling," "False range," "Diff-anchored prose," "Fractal summary," "Hollow content," "Humanizer signature," "Promotional varnish") — the narrative guide overstates what the deterministic tool can actually catch.
- **Several benchmark "reference" candidates are near-identical to their source text**, e.g. `evals/reference/minimum-edit.txt`, `dialect-restraint.txt`, `uncertainty.txt`, `legal-scope.txt` are byte-for-byte or nearly byte-for-byte copies of the corresponding `source` field in `evals/benchmark.json`. Combined with `scripts/run_benchmark.js:49-57` using plain `includes()` substring checks for `required`/`protected`/`forbidden`, most fidelity cases would pass by simply returning the unedited source — the benchmark cannot distinguish "correctly minimal edit" from "no edit performed."
- **`scan` does not use the BOM-aware, encoding-strict reader that `fix`/`report`/single-file commands use.** `runScan` (`bin/prose-lint.js:167`) calls plain `fs.readFileSync(file, "utf8")`, while `readInput`/`decodeUtf8` (`bin/prose-lint.js:46-61`) explicitly validates UTF-8 and refuses invalid encodings for single-file commands. A repository scan will silently mis-decode a non-UTF-8 file instead of refusing it as the single-file path does.
- **`imaginary-objection`'s regex includes `"to be clear"`** (`rules/patterns.json:112`) — a phrase with no inherent rhetorical-objection meaning, likely to fire on ordinary clarifying prose ("To be clear, this only applies to...") and produce false positives disproportionate to its intent.
- **No SEO mode whatsoever.** A content team using this to prep blog/marketing copy for search has zero built-in protection for keywords, headings, meta description, or schema — a capability humanizer-pro has as a first-class modifier.
- **No language auto-detection or dialect handling of any kind**, unlike humanizer-pro's `lang.js` Arabic-script-ratio and dialect-marker heuristics; the caller must always supply `language` explicitly or pattern checks silently produce zero findings (`lib/prose-core.js:349`).
- **The only completed comparative evaluation (`evals/RESULTS.md`) is model-judged, not human-judged** ("Generation and judging used the same model within each run," `evals/RESULTS.md:21`), and the repo openly states it has no completed human-preference result (`evals/HUMAN_EVALUATION.md:13`) — despite building the tooling to collect one. This is the same class of weakness humanizer-pro documents about itself in REVIEW-HANDOFF 3.11.
- **The persona/voice system has no named preset profiles** (no casual/professional/technical/warm/blunt options like humanizer-pro) — voice must always be derived from a supplied sample; there is no fallback persona catalog.
- **`ACKNOWLEDGMENTS.md:12` notes one reviewed-for-comparison-only project** (`jalaalrd/anti-ai-slop-writing`) whose README claimed MIT but had no license file — handled correctly (no code copied), but it shows the general risk class of leaning on eight separate upstream "clean-room comparisons" for design ideas without per-idea provenance tracking (contrast with humanizer-pro's `docs/PROVENANCE.md` pattern-ID-to-upstream-line mapping).
